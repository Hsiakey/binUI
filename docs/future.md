## 语言分工：实现全是 C++17，最底下那一圈 ABI 仍保持 C

| 项目 | 实现语言 | 对外边界 |
|---|---|---|
| binGPU | **C++17** | `.cpp` 实现（RAII / 容器 / 内部异常）；`bingpu.h` 是**C 兼容**的扁平 ABI，C 与 C++ 都能 include |
| bin2d | **C++17** | 对外是 C++ 头（`bin2d/*.h`）；对下调 binGPU 的 C 头 |
| bin3d | **C++17** | 对外是 C++ 头；对下调 binGPU，横向直连 bin2d（C++ 对 C++） |

**为什么 ABI 用 C 而实现用 C++**（这两件事一开始被绑在一起，2026-11-15 分开）：

1. **ABI 的选择看"谁要 include 它"**：`bindings/` 里 Python / Go / Rust 只吃 C 接口。binGPU 是
   C ABI，意味着它们想画 2D/3D 可以直接绑，不必等 binUI 的 C ABI 扩到"绘制"那一大片。这个理由
   跟**用什么语言实现**无关 —— C++ 写、导出 C 符号是 Vulkan loader / HarfBuzz / bgfx / Skia 的
   常规做法。
2. **实现语言按表达力选**：这一层要的是句柄表、容器、生命周期、错误串拼接，在 C 里全是手写样板
   （`std::vector` 换成手动 realloc + 容量字段、两条销毁路线各写一遍析构）。收益为零，维护成本
   却压在每一处；四层统一 C++17 之后，工具链、静态链接参数、风格也一致了。
3. **"C 更快"不成立**（见本节末的实测）：语言本身不改变汇编，差别只在"能不能把取样器内联掉"。

**硬约束（ABI 面与实现面分开写）**：

- **ABI 面**（`include/bingpu.h`）：只有定长 POD + `uint64_t` 句柄 + 扁平函数，**必须能被纯 C
  编译器单独编过**（`make abi-check` 用 `gcc -x c` 编一遍，并 grep 禁掉 `namespace` / `class` /
  `template` / `std::`）。句柄是 `uint64_t` 而不是指针 —— 跨语言传指针是被绑语言的噩梦。
- **实现面**（`.cpp`）：C++ 抽象后端接口 + RAII，内部随便用 `std::vector` / `std::string` /
  `std::unique_ptr` / 异常；但**异常绝不越过 ABI** —— 每个 `extern "C"` 入口 `noexcept` + 顶层
  try/catch，`bad_alloc` → `BGPU_ERR_OUT_OF_MEMORY`，其余 → `BGPU_ERR_BACKEND_FAILED` 并把
  `what()` 写进 `bingpu_last_error()`。
- **没有回调**：device lost / resize 这类事件用显式轮询（`bingpu_poll()`）在渲染线程上取。一旦
  有回调，就要处理"回调里再进 GPU 层"的可重入问题 —— 那是最贵的一类 bug。
- **销毁顺序仍由调用方保证**（C ABI 上没有析构）：bin2d / bin3d 各包一层 C++ RAII（`Device`
  持有句柄、析构里 destroy），把"先销毁子资源再销毁设备"收在**一处**、别让每个调用点自己记。
- **唯一的对外代价**：静态库会带 libstdc++。用 C ABI 绑它的语言在链接时要么让它把运行时静态
  链进去、要么自己带一份；这条写进了 binGPU 的 `docs/abi.md`，不藏着。

**方向仍是单向的**：bin2d / bin3d / binUI 都只**消费** binGPU 的头，谁也不把自己的 C++ 类型
泄回那一层。

### 附：「纯 C 会不会更快」——实测过，不会

master 问过：bin2d/bin3d 是图形 API，写成纯 C 是不是更快、"引擎才适合 C++"。
**结论：语言本身不带来速度，汇编层面是没有区别的。** 同一份 alpha 混合内核分别交给
`gcc -O2` 和 `g++ -O2`（MinGW 15.1.0，`-S -masm=intel`），生成的 `.text` **逐行相同**，
唯一的差异是符号名（`blendRow` vs `_Z8blendRowPjPKjij`）。

真差别的不是语言，是**能不能把每行的取样器内联掉**。照 binUI 的条带发射写了个对照
（本地临时程序 `build-mingw/langtest/bench.cpp`，构建产物目录不入库；`g++ -O2`，200 次 ×
1.6M 像素，取三次最好）：

| 窄条带（4px 宽 × 40 万行） | 耗时 | 相对纯铺 |
|---|---|---|
| 纯铺一个颜色（下限） | 46.2 ms | — |
| 取样器经**函数指针**传入（C 的唯一写法） | 51.3 ms | **+11.0%** |
| 取样器作**模板参数**（可内联） | 46.9 ms | **+1.5%** |
| 取样器走 `std::function`（每行一次类型擦除） | 110.1 ms | **+138.4%** |
| 取样换成渐变数学（每行插值三个通道） | 128.3 ms | **+177.8%** |

宽行（1920px × 1080）时以上全部落在 ±3% 噪音里 —— 那种时候瓶颈是写内存的带宽，跟怎么调用无关。

读法：

1. **C 与 C++ 的差距只有 0~11%，只在窄条带上可见**，而且这点差距用 C 的宏也能拿到（生成特化
   版本）；它不是"语言优势"，是"内联优势"。
2. 真正的大头是**取样数学本身**（+178%）和**类型擦除**（+138%）—— 前者跟语言无关，
   后者是 C++ 自己挖的坑（`std::function` / 虚函数 / 每行堆分配），C++ 里躲开它就行。
3. 所以语言该按**表达力和 ABI** 选，不该按"谁快"选：想让别的语言用，就导出 C ABI（跟用什么
   语言实现无关）；想少写容器/生命周期样板，就用 C++ 写、C ABI 导 —— Vulkan loader、
   HarfBuzz、bgfx、Skia 都是这个套路。

落到这三个项目上就是：**四层都用 C++17 写**，而 binGPU 对外挂一层 C 兼容 ABI（它是最可能被别的
语言直接 include 的一层，所以边界用 C）。"是 API 就得用 C"不成立，"是引擎就得用 C++"也不成立 ——
真正的分界线是"这一层要不要给别人直接 include"，以及"那道边界是不是 C 兼容"。

**迁移状态（重要，别误读）**：binUI 现在**仍然用自己那份光栅数学**（`binui_paint.h` 的条带 +

搬完必须 GL / VK / D3D11 **三端像素基准 0 diff**、示例无回归，功能扩展另开一版。这也解释了为什么
两边暂时各有一份"填充/描边"代码：binUI 那份绑着 `BinUIPaintNode`，是节点的产物；bin2d 那份是
节点无关的画布接口 —— 合并时删掉的是**条带生成**那一层，不是像素语义。

**bin3D 不行**（浮点光栅化顺序不同，z 竞争处必然差 1 像素），它的 roadmap 把容差规则写死了：
轮廓容差 ≤1px、8×8 分块覆盖率 ±2%、平坦区色差 ±2、禁止在 z 竞争处取样。

## 图层设施（P0-1 / P1-7 的收口）—— 设计稿

0.16.8 把父元素的 `opacity` 级联下去了（逐元素乘 alpha），但那只解决了 80%：子元素互相重叠时
重叠区会叠深，而且"内容没变也要每帧重算条带 + 全量重传顶点"没有任何改善。两件事都指向同一个
设施：**离屏图层**。

**状态（0.16.12）**：接口与 **GL / D3D11 / Vulkan 三个后端全部完成**，三端像素逐位相同。

- 0.16.9 GL：离屏 FBO + 纹理（按窗口大小，池 4 层）；
- 0.16.10 D3D11：第二张 `offTex` + SRV + RTV；
- 0.16.11 层作用域修正：owner 自己的底色/边框也进层（否则合成时拿"已经被淡过一次的父底"
  当背景，整体暗一档）；
- 0.16.12 Vulkan：**整条渲染路径改用 dynamic rendering**（`vkCmdBeginRendering` /
  `vkCmdEndRendering` + `VK_PIPELINE_RENDERING_CREATE_INFO`），绕开 render pass /
  framebuffer 的附件布局交互，一次打通。细节与实测见
  [`docs/vulkan_design.md`](vulkan_design.md) §7.13。

只对"绘制顺序连续、覆盖 ≥2 个节点"的半透明子树建层；拿不到动态渲染的老驱动上
`pushLayer` 返回 false，退回逐元素近似（像素与 0.16.8 完全一致）。层缓存（P0-1）仍是空白。

**为什么 render pass 那条路走不通**（记下来，免得以后又想"用 render pass 不是更简单"）：
两轮尝试都卡在同一组现象上 ——

1. 主 pass 重启后（`EndRenderPass` → 再 `BeginRenderPass`，attachment0 是 `LOAD_OP_LOAD`），
   重启之前画到主目标上的内容（页面底色、层外的图元）**消失**；
2. 层里 **owner 自己那一笔**（父元素的底色）在最终画面里不出现，而它的子节点正常。

换了动态渲染之后两条现象**同时消失**，说明它们确实是"MSAA 附件 + 中途重启 render pass"
这一组行为的问题，不是层内容本身画错。

**接口**（加在 `IBinUIGfx`，与 `setTextSubpixel` 一样"默认不实现"）：

```cpp
// 把接下来的绘制收进一块离屏图层；alpha < 1 时 pop 后整体合成。
// 返回 false = 后端不支持 → 调用方退回"逐元素乘 alpha"（0.16.8 的行为），其他后端零改动。
virtual bool pushLayer(float x, float y, float w, float h, float alpha) { ... return false; }
virtual void popLayer() {}
```

**渲染器侧**：绘制遍历前把"同一层作用域的节点是否在绘制顺序里连续"算出来（父先于子、同 z 连续
——普通布局都满足）；连续的才包层，不连续的退回逐元素模式。这样不需要改 `drawOrder()` 的语义。

**后端实现要点**：

- **GL**：离屏 FBO + 纹理，按窗口尺寸分配、池化复用。`pushLayer` = `flushAll()` → 绑层 FBO →
  clear 透明；`popLayer` = `flushAll()` → 绑回原 FBO → 用白色纹理画一个带 alpha 的四边形。
- **D3D11**：第二张 `offTex` + SRV，`OMSetRenderTargets` 切目标；pop 时用同一条像素着色器采样
  层纹理（现有 `emitQuad` 已经有 SRV 通路）。
- **VK**：动态渲染下 `endRendering` → `beginRendering(层图)` → 画 → `endRendering` →
  `beginRendering(主目标, LOAD)` → 合成四边形。层图在 `COLOR_ATTACHMENT ↔ SHADER_READ_ONLY`
  之间往返，主目标在每层进出各一次（代价见 vulkan_design §7.13.6）。

**已知边界（不是 bug，是取舍）**：层目标是**单采样**的，所以组边界靠"合成四边形在主目标 4x MSAA
上的覆盖率"抗锯齿（小数位置是对的），但组**内部**的小数几何没有 MSAA，边缘硬一档；各后端在这类
边缘的采样归属也会差（`scale(0.77)` + `opacity` 用例：VK 与 D3D11 逐像素相同，GL 差 128 个边缘
像素）。要彻底消掉得把层目标做成 4x MSAA + resolve，显存 ×4（4K 上单层 132 MB），见
[`docs/vulkan_design.md`](vulkan_design.md) §7.13.7。下一步更值得做的是**按元素尺寸**分配层目标
（显存和 clear 带宽都跟着元素走），顺带就能把 MSAA 打开。

**层缓存**（P0-1 的本体）：同一个层作用域在"内容签名没变"时，直接重放上次的图层纹理，跳过
条带生成与顶点上传。签名 = 子树里每个节点的矩形 + 颜色 + 文本 + 滚动偏移 + 动画值；任一项变化
就重建。这里必须承认代价：**这是给渲染器引入第一份"跨帧缓存生命周期"**，0.16.x 那一串抖动/空转
的 bug 都与"状态没清干净"有关，所以缓存要有明确的失效出口（布局代数 + 每节点版本号），
并且允许整体作废（`invalidateLayers()`）兜底。

**验收**：

- 不支持层的后端必须逐像素不变（0 diff）—— 这是 `pushLayer` 返回 false 的全部意义；
- 支持层的后端在"纯色/渐变/文字"上必须与逐元素模式逐像素一致（重叠场景除外，那里的差异是
  **修对了**）；
- 缓存生效：一页静态卡片，`BINUI_PERF=1` 的"绘制"从 ~1 ms 掉到 ~0，且条带生成次数 = 0。

**风险**：三端 render pass / 目标的差异（VK 最重）；层纹理内存（需要池化 + 上限）；
透明窗口（`setTransparent`）下预乘 alpha 的合成要额外验一遍。

## 欠缺清单（2026-11-14 实测，按优先级）

跟 Skia / 浏览器比，binUI 现在缺的东西都在这里，一条一条带证据（数字或代码行），并标了
**谁来填**（binUI 本体 / bin2d / bin3d / binGPU / 明确不做）。这是**欠账清单**，不是愿望单：
标"不做"的就是决定了不做，附理由，免得以后又从头讨论一遍。

### P0 — 决定"会不会输给 Skia"（可测的数量级差距）

| # | 缺什么 | 现在的证据 | 谁填 | 验收 |
|---|---|---|---|---|

#### 绘制成本现状（v0.16.33 实测，两个工具可复现）

以前这一节只有几句一次性手测数字（"约 1052 µs/帧、约 9800 个四边形"），既不能复现，
也没法当门禁 —— 优化完无法证明真的快了，重构也无法证明没画歪。v0.16.33 补上两个入口：

- `make bench-draw`：纯 CPU 遍历（计数后端，**无 GPU / 无窗口 / 确定性**，跨后端可比）；
- `make bench-gl`：真实 GL 后端一帧，把"绘制(遍历+发射)"和"上传+绘制调用（`flushAll`）"
  分开报。**不含** MSAA resolve / SwapBuffers —— 窗口一进交换链，present 就被合成器
  节流到 8.2 ms/帧（正好半个刷新周期），量到的就不是 CPU 成本了。所以 `gl_shot --bench`
  走新加的 `flushFrame()`（只 flushAll，不 resolve 不 swap）。

四条结论（它们直接决定了后面做什么）：

1. **中等页面的遍历已经不是瓶颈**（几十微秒）。0.16.33 之前不是这样：节点循环里有一处
   `std::getenv("BINUI_DEBUG_CLIPMASK")`，实测 **896~928 ns/次**，每个节点白烧近 1 µs ——
   features 102 → 28 µs、animshow 152 → 38 µs、svgdemo 68 → 15 µs。
   规矩：**节点循环里只许出现 `static const` 的结果，不许有函数调用**。
2. ~~唯一还在"上万四边形"量级的是任意角度渐变的条带~~ —— **已解决（0.16.34）**：
   四角带色四边形把 43,409 条变成 12 个四边形（5 MB → 12.8 KB，绘制 0.288 → 0.007 ms）。
   注意到这一步之后，**binUI 里再没有"上万四边形"的场景了**（最大的 texturedemo 是 7,606 个
   小矩形，来自 `<canvas>` 回调自己画的东西）。
3. **"批量原语"没有收益**（v0.16.33 试过又撤回）：把上千条 `fillRect` 合成一次
   `fillBands` 调用，GL 实测 0.299 → 0.288 ms（3.7%，在噪声内）—— 条带贵在"写 6 个顶点"，
   不贵在虚调用。所以不要再从"减少调用次数"这个方向使劲，要减的是**四边形数量本身**
   （0.16.34 就是这么做的）。
4. **"脏节点上传"的适用面很窄**：脏矩形已经只重画变化区，同几何重复发的场景只剩
   "整窗重绘"（resize / 滚动 / 整页动画），而整窗重绘的上传量级现在是几百 KB/帧。
5. **图层本身很便宜（v0.16.35）**：4 个 opacity 组一帧只多花 ~4 µs（绘制 0.013 ms，逐元素
   0.009 ms）。但**修之前是 0.097 ms** —— 多出来的 84 µs 全是 GL 的
   `glGetIntegerv(GL_FRAMEBUFFER_BINDING)`（pushLayer 每层一次，同步查询要 drain 流水线）。
   教训：**GL/D3D 的后端代码里不许出现同步状态查询**（`glGetIntegerv` / `GetData` /
   `Map(READ)`），需要知道什么就自己维护。这条也是 P0-1「层缓存」被关掉的理由：
   能省的上限只有 4 µs。

### 已做的新能力（不在欠缺清单里，但值得记一笔）

- **淡出渐变的插值空间（v0.16.38）**：全链路改成在预乘空间插值（CSS Color 4），淡出

- **VK 图层管线选错（v0.16.45）**：最外层离屏图层用了 4× MSAA 主管线（层目标单采样），
  圆角图片的弧线每行差 1px（17 px / 通道差 200+，从 v0.16.12 起就存在）。修好之后
  `filter-blur` 最大通道差 20→1、`drop-shadow` 58→2、`blur-quality` 48→1，

  判据用例 `anim/round-in-layer`（opacity 层 / 模糊层 / 小数坐标 / 嵌套两层 / 层里的圆与细线）。
- **真高斯模糊（v0.16.44 / 格式 v33）**：三条模糊路径（`backdrop-filter` / `filter: blur` /
  `drop-shadow`）换成"降采样到 σ 还剩 ≥2 纹素的那一级 + 横/纵两趟密采样加权卷积"。
  抽头每纹素一个、覆盖 ±3σ、**加法混合**累加（GL `ONE/ONE`，VK 新加 ADD 管线变体、
  D3D11 新加 ADD 混合状态），权重和正好 255 → 预乘色的加权平均（真卷积），不需要着色器。
  σ = 半径（CSS 口径），外扩 3σ 与 `PaintFilterBlurPad` 天然一致；旧链的等效 σ 只有半径的
  1/4，所以观感"更糊"是修正。规则与抽头算法提到 `include/binui_paint.h` 由三端 + 测试共用。
  量测里挖出并修掉三处：**抽头按 ±kσ 布点会留空档**（卷积核成梳状，输出带栅栏）、
  **浮点权重被截断进 uint32_t**（核退化成 delta，"模糊完全没生效"）、
  **`ensureBlurLevel` 的 resize 让 `BlurLevel&` 悬空**。
  门禁：GL vs VK 0 不同像素（`filter-blur` 最大通道差 59 → **20**），D3D11 1~2，
  GDI 16 例 0 差异；`filter-blur` 的 10~90% 过渡带从 10px 变成 39px（σ=18）。
  证据图 `docs/issues/assets/blur-quality.png` + `blur-quality-before.png`（改前 14px 圆点是个十字）。
- **`filter: drop-shadow(...)`（v0.16.43 / 格式 v33）**：**元素轮廓**的投影（取元素自己的 alpha 上色，不是盒子），与 `filter: blur` 共用同一套离屏图层：阴影色铺满 → 保留混合（`dst *= srcA`）乘上层内容的 alpha → 同一条降采样链 → 按偏移（取整）合成；多条按书写顺序（写在前面的在上层），颜色可写在任意位置、缺省 `currentColor`。顺手修掉两个既有缺陷：**GL 的轮廓采样 V 方向写反**（不对称形状的影子会上下镜像）、**D3D11 的降采样链没还原 scissor**（之后画的内容被裁在最后一级的大小里，表现为文字整行消失）。三端 0 不同像素（最大通道差 58 / 2）。证据图 `docs/issues/assets/drop-shadow.png`。模糊质量在 v0.16.44 换成真高斯（见上一条）。
- **`filter: blur(Npx)`（v0.16.42 / 格式 v32）**：元素**连同整棵子树**的离屏模糊。
  与 `opacity` 共用同一条图层（同时写两者只建一层），模糊本体与毛玻璃**同一条算法**
  （抓层纹理而非当前目标；合成用正常 alpha 而非 replace；v0.16.44 起降采样 + 分离高斯）。图层框与合成矩形按 3σ 外扩
  并**取整**，所以"糊出来的边"落在像素边界上、三端逐像素对齐（GL vs VK 0 不同像素、
  最大通道差 59 → **20**（v0.16.44 真高斯，圆角图片那条既有差异被 2×2 平均摊平）；
  D3D11 vs GL 0 不同像素、最大通道差 2）。半径上限 64px（钳制并告警），
  百分比按 0 处理并告警，`blur(0)` 不建层。证据图 `docs/issues/assets/filter-blur.png`。
  顺带在量测里确认了一条**既有**差异（见下面「工具链已知问题」最后一条）：层里的圆角图片。
- **任意角度渐变 = 四角带色四边形（v0.16.34）**：`IBinUIGfx::fillGradientQuad` + 共享的

### P2 — 明确不填（附理由）

- **GPU 路径光栅 / tessellation**：打破"后端只有 fillRect"这条契约，三端 0 diff 的像素基准随之
  报废；收益只在极端路径场景，不值。
- **文字次像素（ClearType）**：灰度 AA 在任意背景 / 缩放 / 旋转下都稳，次像素只在整数落位时
  成立，和 binUI "动画文字可亚像素"的方向直接冲突。
- **完整 SVG 滤镜栈 / SMIL / `<tspan>` 富文本**：投入产出比不成立 —— 这类素材应该在资产侧
  预处理成路径/位图。
- **通用图形 API 化**（bindless、光追、GLES·Metal 全家桶）：见 binGPU 那节的"明确不做"。
- **遮罩内容跨亮度重叠的"乘两次"**（v0.16.26 起的已知边界）：要修对，得在遮罩图层里
  **再开一个子层** —— 先把 mask 内容用正常 alpha 合成画进去、再把整层乘一次，三端各要
  多一个离屏目标与图层池管理。而它只在"不同亮度的形状互相重叠"时才可见：同亮度已经按
  nonzero 合并成一条几何。代价（每帧多一次图层建立 + 一次全层乘法）与收益（窄到需要专门
  构造才看得见）不匹配，所以标不做。绕法：mask 内容用同一亮度，或 `mask-type="alpha"` 配
  同色几何。
- **仿射节点上的毛玻璃**（v0.16.27 起的已知边界）：要正确得给"仿射圆角 + 屏幕 UV"做一套
  新几何（现在 `BuildImageBands` 的圆角条带是轴对齐逐行的，旋转后圆角弧线会歪），三端各一份。
  而旋转容器里放毛玻璃是罕见组合，现在退回半透明底（`drawNodes` 里 `!affine` 那个判断）
  视觉上是"没糊，但底还在"，比糊错更稳。
- **P0-4 脏节点顶点上传**：v0.17.3 用实测重估过（见上面 P0 表第 4 行）。顶点量确实比旧账大（svgdemo 819 KB 而不是估算的 288 KB，描边改 CPU 条带后涨了 2.8 倍），但**上传耗时只有 0.026 ms/帧 = 帧预算的 0.16%**，而且已经贴着内存带宽（~32 GB/s）。脏节点上传要换来的是一套「节点 → 顶点区间」映射 + 跨帧失效管理，它能省的上限就是这 0.16%，所以标不做。真要压这块，顺序应该是先减四边形数（描边条带已经是最少的正确解；渐变早在 0.16.34 就四边形化了），而不是改上传路径。
- **静默画错**（如 0.16.14 的 `RoundRect` 右/下各短一行导致环与环之间漏一圈亮线、透明条带把
  兄弟元素的阴影擦成白块；0.16.16 的 `AlphaBlend` 源位图未选中导致文字阴影整块不出现）
  —— 这类如果不修，GDI 基准图就失去意义；
- 与主线**语义**不一致（不是"边缘差几十像素"，而是"该画的不画/画错位置"）。

**已知差异（明确不修）**：

| 差异 | 原因 | 记录 |
|---|---|---|
| 标签文字被上下裁掉（`div` 默认 `padding:8` + 大字号） | `DrawTextW` 按文字矩形裁剪，GPU 侧只裁节点盒 | [`docs/issues/09-gdi-text-clip.md`](issues/09-gdi-text-clip.md)（WON'T FIX，带复现资产） |
| `box-shadow` 环边界吸整像素 | GDI 没有 AA 填充 | `docs/pixels/shadow.png` 就是 GDI 基准；`pixels-vk` 三端 0 差异 |
| 组透明度逐元素近似（重叠区略深） | GDI 没有离屏合成面 | P1-7 的"剩下的" |
| emoji 无 `text-shadow` | 彩色格子乘阴影色会糊成彩团 | 与 GPU 端一致（GPU 也明确不画） |
| ¼ 像素字形相位不适用 | GDI 的文字位置本来就会被 `DrawTextW` 吸附 | 只在主线三端 |

**对欠缺清单的影响**：下面 P0/P1 条目的"谁填"一栏里凡是提到 GDI 的，一律按**只做主线三端**读；
`docs/pixels/` 的基准仍由 GDI 生成，但"和 GPU 端逐像素一致"的判据只对 GL/VK/D3D11 生效。

## bin2d —— 2D 绘制核

**定位**：保留模式的 2D 画布库（场景图 + 图层 + 合成），不认节点、不认布局、不认窗口，可以在
没有 UI 的地方用。宿主有两类：binUI 的 `<canvas>`，以及任何"要画点东西"的程序（报表、图表、
导出截图、票据打印）。

**语言**：C++17（和 binUI 同标准、同构建）；对外是 C++ 头，对下调 binGPU 的 C 头。

**要补的本体**（按实现顺序）：

1. **场景图**：`Scene → Layer → Shape`，形状 = 填充/描边/文字/图片/路径引用。现在 binUI 是
   "遍历节点树 → 现算条带 → 立刻 fillRect"，中间没有可保留的东西，所以每条路径每帧都重算。
2. **变换栈 + 裁剪栈的合并**：现在只有 `pushClip` 求交（轴对齐）；2D 库要有"任意变换 + 圆角
   裁剪 + 组透明度"，组透明度必须靠离屏合成，不能靠逐个形状乘 alpha（重叠处会露）。
3. **离屏目标与合成**：图层 = 一张 RGBA 位图，`blend(layer, dst)` 支持 `src-over`，再加
   `multiply` / `screen` 两三种就够。这一步顺带解决一个现成的痛点 ——
   `<canvas>` 里的内容**离屏渲染拿不到**（`tools/offscreen_render` 只能得到空画布，
   `docs/img/svgdemo|texturedemo|cubedemo` 三张图为此只能真机截屏）；有了离屏合成，
   canvas 内容也能进基准图和文档。
4. **滤镜**：投影、模糊（两次可分离盒式即可）、灰度/色相。投影是 UI 里最常要的，现在得靠
   半透明圆角叠一层来假造。
5. **图像重采样**：`drawImage` 现在任意尺寸都能画（后端是 bilinear 采样），缺的是**质量**：
   没有 mip 链（大图缩小会闪）、没有圆角裁剪、没有 tint、没有九宫格；2D 库要把这套补齐。
6. **导出**：`renderToRGBA()` 拿一帧位图 → PNG（自己写极小 PNG 编码，或直接 dump 裸 RGBA）。

**怎么抽**：新建独立目标 `bin2d`，源 = 现在的 `binui_path.h` + `binui_paint.h` + 新的
`Scene/Layer/Compositor`；binUI 变成它的**消费者**（`CanvasFn` 的参数从 `IBinUIGfx&` 换成
`bin2d::Canvas&`，应用写路径/图层，binUI 只负责把结果按条带刷到后端）。反向依赖不允许：
bin2d 里出现 `BinUINode`、`flex`、"节点盒"这些字眼就说明抽错了。

**开工条件**（满足任一）：

- 出现"多图层要合成 / 要投影 / 要组透明度"的界面，靠叠半透明圆角已经糊弄不过去；
- `<canvas>` 里的手绘代码超过一屏语义（现在 `svgdemo`/`texturedemo` 各百来行，还行）；
- 有非 UI 的宿主想直接用这套光栅（打印/导出是最可能的先来者）。

**验收线**：搬家那一版必须 **GL/VK/D3D11 三方像素基准 0 diff**、8 个示例无回归；功能扩展
放在搬家之后单独提，别混在一个提交里。

## bin3d —— 3D 渲染器

**定位**：小型实时 3D（场景图 + 相机 + 深度 + 光照），目标是"界面里嵌一块可交互 3D"，
不是引擎 —— 不追 PBR、不追后处理、不做资产管线。

**语言**：C++17；对下调 binGPU 的 C 头，横向直连 bin2d（C++ 对 C++）。

**现在的缺口**（都在后端，一条都不小）：

| 缺口 | 现状 |
|---|---|
| 深度附件 | 三端只有颜色附件，没有任何 depth/stencil |
| 用户着色器 | 各端一套固定管线；VK 的 SPIR-V 是 `src/backends/binui_vk_shaders.h` 里的常量数组 |
| 顶点/索引缓冲上传 | 顶点是每帧 CPU 生成的一整块常驻映射缓冲（见 `docs/vulkan_design.md` §5.1） |
| 相机/矩阵 | 完全没有；`examples/cubedemo` 里应用自己算 MVP、用 `fillLine` 画线框 |
| 贴图到面 | 平面上的任意四边形已有（`emitQuadUV` + `setAffine` 状态，0.16.18/0.16.21）；透视（3D 投影后）没有 —— 那是 binGPU 的事 |

**路线（先说选哪条）**：**先软光栅，后 GPU**（GPU 阶段落在 binGPU 上，见下面「真不够用时」）。

软光栅版 = 三角形填充 + z-buffer + 双线性贴图，直接复用 bin2d 的扫描线与 `include/binui_path.h`
的求交，纹理走现有的 `prepareImageRaw`（RGBA 直传）通路。UI 侧只需要一个新的
`BINUI_3DVIEW` 节点类型：每帧把渲染结果当纹理上传，后端零改动 —— GDI 也能跑，离屏渲染也能出图，
像素基准可测。

好处是先把产品问题问清楚："嵌一块 3D 到底长什么样、要多快"。代价是 CPU：一个 640×360 视口
一帧就是 23 万像素的覆盖，软光栅能撑住 60fps 的覆盖量大概在 30 万像素以内（单个核），
再大就不行了。

真不够用时才进 GPU 阶段，而那条路走 **binGPU**（不是往 `IBinUIGfx` 里塞 3D 原语）：
`bingpu` 加网格创建 + 深度附件 + 自定义着色器，bin3d 只是它的调用者。**binUI 这边需要的仍然只有
"一张纹理"** —— 3D 视口渲染到 binGPU 的离屏目标，再把结果按 `prepareImageRaw` 的 RGBA 交给
`IBinUIGfx`，UI 的三个后端一行都不用改。这条分工是 binGPU 存在的另一个理由：它让"加 3D"不至于
变成"改三个 UI 后端"。

**这一步要提前认一件事**：3D 的像素基准不能再用"0 diff"——浮点光栅化顺序不同，z 缓冲边缘必然差
1 个像素，三端 diff 的容差规则必须重写（用覆盖率/轮廓容差，而不是逐像素比）。否则"三端像素
一致"这条底线会把 3D 拖成永远合不进去的分支。

**开工条件**（同时满足）：

1. 真出现"界面里要放能转的模型"的需求（不是"能画个立方体"，那个 `cubedemo` 已经能做）；
2. 软光栅版在目标视口尺寸上撑不住 60fps。

没到这两条就不做：3D 的工程量（驱动差异、着色器编译、资源生命周期）和 binUI 现在的验收方式
冲突，接进来会拖慢 UI 主线。

## binGPU —— GPU 抽象层（三个后端下面那一层）

**定位**：一份"设备 / 交换链 / 资源 / 管线 / 命令 / 呈现"的抽象，Vulkan 与 D3D12 各一个实现。
binUI、bin2d、bin3d 只写"怎么画"，不再各自维护一份交换链。

**语言**：**实现 C++17**（RAII、容器、内部异常），**对外是 C 兼容的 ABI** —— 头文件里只有定长
POD + `uint64_t` 句柄 + 扁平函数，没有回调；C 与 C++ 都能直接 include（理由与硬约束见上文
「语言分工」，以及 binGPU 仓库自己的 `docs/abi.md`）。

**为什么看起来该做**：同一件事现在写了三遍，而且每一遍都是完整的一份生命周期：

| 每份都要自己做的事 | 现状（`src/backends/`） |
|---|---|
| 设备 / 上下文 / 交换链 | `wglCreateContext` 9 处、`vkCreateSwapchainKHR` 5 处、`CreateSwapChainForHwnd` 2 处 |
| 管线 / 着色器程序 | `glCreateProgram` 4 处、`vkCreateGraphicsPipelines` 4 处、`D3DCompile` 3 处 |
| 着色器源码 | GLSL 内联 / `binui_vk_shaders.h` 的 SPIR-V 常量数组（101 行）/ HLSL 内联 —— **同一件事三套源码**，改一个 uniform 要动三个文件 |
| 代码量 | GL 1327 行、D3D11 1340 行、VK 2805 行（显式同步与描述符让 VK 自然是别人的两倍） |

`IBinUIGfx` 只约束了"怎么下发 7 个原语"，**没约束"设备怎么来"** —— 所以窗口、交换链、纹理上传、
present 阻塞语义这三件事在每个 `.cpp` 里各有一份，驱动差异的补丁也是三份。

**已经抽出来一半的东西**（binGPU 的地基）：

- `presentPacesFrames()`（`src/backends/binui_gfx.h`）：把"谁当节拍器"从三个外壳里提炼成一个
  接口返回值 —— 这正是 GPU 层该有的抽象形状；
- `docs/vulkan_design.md` §1 的六条契约、§5.10 的三路 present、§6.1 的鲁棒性清单，
  其实已经是 binGPU 的需求文档，只是现在还挂在 Vulkan 名下；
- VK 后端那套同步模型（fence + 单帧在上 + 帧内上传）是唯一一份"写对了"的显式同步代码，
  搬进 binGPU 就是它的 VK 实现。

**路线（先说选哪条）**：

1. **只抽一层薄的固定管线**：2D 四边形 + 纹理 + 深度附件 + 可选顶点上传，恰好覆盖
   `IBinUIGfx` 现在需要的，再加 bin3d 将来要的 `drawMesh`。
2. **先做 VK 实现**（照 `binui_vk.cpp` 已有的同步模型**用 C 重写**一遍，见下条），
   **D3D12 作第二实现**（替换 D3D11 那条路；D3D11 保留为老机器兜底，不迁）。
3. **GL 不迁**：状态机抽象收益最低，而它是老驱动 / 远程桌面 / 无 GPU 环境的兜底 ——
   迁过去只会得到一份"假装自己是现代 API"的 GL 封装。

**C 的额外成本要说在前面**：`binui_vk.cpp` 那 2805 行是 C++，搬进 binGPU 不是"移文件"而是
"按 C 重写"（没有 `std::vector` 存交换链 image、没有 RAII 管 fence、没有 `std::string` 拼错误）。
好消息是 Vulkan 自己的结构体本来就是 C 的，`VkDevice`/`VkCommandBuffer` 那套直接就能用；
坏消息是容器和生命周期要自己写，估计比重写一遍 D3D12 实现便宜不了太多。换回来的是一份**任何
语言都能直接绑**的 GPU 层 —— 这笔账在"第四份后端"出现时才划算，见下面的开工条件。

**明确不做的**：不追通用图形 API（bindless、pipeline cache 托管、光追、GLES/Metal 全家桶）。
一旦把它做成"跨平台渲染引擎抽象"，成本远超 binUI 本身，等于自己重写一个 wgpu。

**开工条件**（满足任一）：

1. bin3d 进到 GPU 阶段 —— 那时要网格 + 深度 + 自定义着色器，binGPU 的每个实现各写一遍；
2. 真要接第四个后端（Linux/X11、Android GLES、Metal），一次迁移要动的点超过"抄一份 `.cpp`"。

**现在不做的原因**：三个后端已经过了像素验收，而**像素一致的功劳恰恰在于"三份实现各自简单
直白"** —— 每份都只是把 `include/binui_paint.h` 算好的条带 `fillRect` 出去，出问题一眼能看出是
哪个后端、哪一行。中间插一层设备抽象，收益是"少写第四份"，代价是所有像素 bug 多一层要排查。
"第四份"还不存在时，这是纯亏。

**验收线**：搬家后三端像素基准仍 0 diff；窗口 / 输入法 / 拖边框外壳（`binui_app.h`、
`binui_gl-gdi.h`）**不认识 binGPU**，只认 `IBinUIGfx` —— 这条边界一旦被打破，这层抽象就白做了。

## 四层关系

```
bin3d  (C++17) ──►  bin2d 核 (C++17)（场景图 / 图层 / 合成 / 光栅数学）
                          ▲
binUI  (C++17) ───────────┘（并排的消费者：布局 + 事件 + 文本，用 2D 核画自己）
                          │
                          ▼
                binGPU (C++17 / C 兼容 ABI)（设备 / 交换链 / 管线 / 呈现）
                          │
                          ▼
                GL（兜底）/ VK / D3D12 —— 这三套 API 自己也是 C
```

四个独立目标（含现有的 binUI）、共用一份光栅数学，验收方式统一成"像素基准 + 三端 diff"。
语言边界只有**一条**：`binGPU` 的 C 头。上面三层都是 C++，谁都可以 `#include "bingpu.h"`；
下面的 GL/VK/D3D12 本来也是 C 接口，所以整条链上没有"语言转换层"这种东西。

**顺带的好处**：binGPU 是 C 兼容 ABI，`bindings/` 里那三条语言（Python / Go / Rust）将来可以直接绑它
画 2D/3D，不必等 binUI 的 C ABI 一路扩到绘制原语。

**和 binUI 发布的关系**：这三个项目都不改 `.bui` 布局、不动 `BINUI_VERSION`，所以可以随时并行
推进；反过来，binUI 的版本号也不会因为它们的进度而冻结。

## 为什么现在只记不改

几何/光栅那层已经干净（纯头文件、无第三方依赖），抽出去的成本主要在**场景图/图层**这一块 ——
而它恰好是 binUI 现在**故意没有**的东西：binUI 每帧重算条带，换来了"没有缓存失效、没有脏状态"
（这在 0.16.x 那一串抖动/空转的 bug 里救过命）。

也就是说：把 2D 场景图加进来，等于给渲染器引入一份要维护的缓存生命周期。**这份复杂度只在
"画面要被复用 > 1 帧"时才有回报**（动画、图层、滤镜）。等真需求来了一次性做，别为了架构好看
先加状态。

三个项目的成本结构不同，别混着评估：bin2d 加的是**状态**（缓存生命周期），bin3d 加的是**另一套
光栅数学**（深度 + 浮点），binGPU 加的是**间接层**（少写第四份实现，但所有像素 bug 多一层）。
所以它们各自的开工条件也写在各自的章节里，不搞"一起开工"。
