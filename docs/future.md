# 未来计划：bin2d / bin3d / binGPU（未实现）

> 本文**故意不进 [`docs/README.md`](README.md) 的索引、也不在 README 提**：这几条还没有一行
> 代码，是方向性记录，不是承诺，也没有日期。真开工时再补索引和 README 里的一句话。
>
> binUI 的边界是**布局 + 事件 + 文本 + 描述式绘制**。下面三个项目是把这条边界外面的几层单独
> 做成库：一层在它**下面**（光栅/合成，bin2d），一层在它**旁边**（3D 视口，bin3d），
> 还有最底下一层**设备与呈现**（binGPU）。
> 三者都不改 `BINUI_VERSION`（不碰 `.bui` 布局，纯新增目标）。
>
> **语言分工（master 定）**：bin3d = C++，bin2d = C++，**binGPU = C**。bin2d/bin3d 跟 binUI
> 同为 C++17；只有最底下的 binGPU 是 C11、导出 C ABI —— 理由见下一节。

## 语言分工：binGPU 用 C，上面两层用 C++

| 项目 | 语言 | 对外边界 |
|---|---|---|
| binGPU | **C11** | 头文件只有定长 POD + `uint64_t` 句柄 + 扁平函数；`.h` 里不能出现任何 C++ 类型 |
| bin2d | **C++17** | 对外是 C++ 头（`bin2d/*.h`）；对下调 binGPU 的 C 头 |
| bin3d | **C++17** | 对外是 C++ 头；对下调 binGPU，横向直连 bin2d（C++ 对 C++） |

**为什么偏偏最底层是 C**（这不是妥协，是三件事凑出来的结论）：

1. **它下面那三套 API 本来就是 C**：`vulkan.h` 是 C；D3D12 是 COM —— C 风格的 vtable，从 C
   里自己声明接口也能调；GL 是 C。用 C 写这一层是顺着接口走，用 C++ 写反而是给 C 接口套一层
   C++ 壳、再让上层隔着 `extern "C"` 打回来。
2. **它是最可能被别人直接绑的一层**：`bindings/` 现在有 Python / Go / Rust 三条绑定，它们全都
   只吃 `include/binui_c.h`，绕开 binUI 的 C++ 接口。GPU 层是 C ABI，意味着 **Rust / Go 想画
   2D/3D 可以直接绑 binGPU，不必等 binUI 的 C ABI 扩到"绘制"那一大片**。
3. **形状合适**：GPU 层传的全是数字和句柄 —— 没有字符串、没有回调、没有可变长结构。正好落在
   [`docs/bindings.md`](bindings.md) 那三条约束（定长 POD / 无回调 / UTF-8）里最省事的位置；
   反过来，场景图、图层、矩阵、容器这些是 C++ 的主场，硬用 C 写等于自己造 vector 和 unique_ptr。

**C 带来的硬约束（写在这，别让实现时才吵）**：

- 没有异常、没有 RAII：设备 / 缓冲 / 管线 / 交换链全是 `uint64_t` 句柄（**不是指针** —— 跨语言
  传指针是被绑语言的噩梦），创建失败返回错误码，错误串走 `bingpu_last_error()` 那种静态缓冲。
- 销毁顺序由调用方保证（C 没有析构）。bin2d / bin3d 各包一层 C++ RAII（`Device` 持有句柄、
  析构里 destroy），把"先销毁子资源再销毁设备"收在**一处**，别让每个调用点自己记。
- 不搞跨线程回调：device lost / resize 这类事件用显式轮询（`bingpu_poll()`）在渲染线程上取。
  一旦有回调，就要处理"回调里再进 GPU 层"的可重入问题，C ABI 上这是最贵的那种 bug。
- 实现可以是 `.c`（纯 C11），也可以按 `src/binui_c.cpp` 的老办法用 C++ 实现 C 接口 —— 但**导出
  的头文件和 ABI 必须是 C**，且不依赖 libstdc++（否则 Rust/Go 那条路直接断）。
- 构建没障碍：`CMakeLists.txt` 已经是 `LANGUAGES C CXX`，加一个 `add_library(bingpu STATIC ...)`
  即可；注意 MinGW 下 `.c` 走 C 编译器，头文件里混进 C++ 语法会在那一步炸出来。

**方向是单向的**：bin2d / bin3d / binUI 都只**消费** binGPU 的 C 头，谁也不把自己的 C++ 类型
泄回那一层。哪天发现要往 binGPU 里塞 `std::string` 或模板，就说明那一层被放错了东西。

### 附：「纯 C 会不会更快」——实测过，不会

master 问过：bin2d/bin3d 是图形 API，写成纯 C 是不是更快、"引擎才适合 C++"。
**结论：语言本身不带来速度，汇编层面是没有区别的。** 同一份 alpha 混合内核分别交给
`gcc -O2` 和 `g++ -O2`（MinGW 15.1.0，`-S -masm=intel`），生成的 `.text` **逐行相同**，
唯一的差异是符号名（`blendRow` vs `_Z8blendRowPjPKjij`）。

真差别的不是语言，是**能不能把每行的取样器内联掉**。照 binUI 的条带发射写了个对照
（本地临时程序 `build-mingw/langtest/bench.cpp`，构建产物目录不入库；`g++ -O2`，200 次 ×
1.6M 像素，取三次最好）：

| 窄条带（4px 宽 × 40 万行） | 耗时 | 相对纯铺 |
|---|---|---|
| 纯铺一个颜色（下限） | 46.2 ms | — |
| 取样器经**函数指针**传入（C 的唯一写法） | 51.3 ms | **+11.0%** |
| 取样器作**模板参数**（可内联） | 46.9 ms | **+1.5%** |
| 取样器走 `std::function`（每行一次类型擦除） | 110.1 ms | **+138.4%** |
| 取样换成渐变数学（每行插值三个通道） | 128.3 ms | **+177.8%** |

宽行（1920px × 1080）时以上全部落在 ±3% 噪音里 —— 那种时候瓶颈是写内存的带宽，跟怎么调用无关。

读法：

1. **C 与 C++ 的差距只有 0~11%，只在窄条带上可见**，而且这点差距用 C 的宏也能拿到（生成特化
   版本）；它不是"语言优势"，是"内联优势"。
2. 真正的大头是**取样数学本身**（+178%）和**类型擦除**（+138%）—— 前者跟语言无关，
   后者是 C++ 自己挖的坑（`std::function` / 虚函数 / 每行堆分配），C++ 里躲开它就行。
3. 所以语言该按**表达力和 ABI** 选，不该按"谁快"选：想让别的语言用，就导出 C ABI（跟用什么
   语言实现无关）；想少写容器/生命周期样板，就用 C++ 写、C ABI 导 —— Vulkan loader、
   HarfBuzz、bgfx、Skia 都是这个套路。

落到这三个项目上就是：**binGPU 用 C（它是 ABI 面，底下三套 API 本来就是 C），bin2d/bin3d 用
C++17 写、需要时再挂一层 `extern "C"` 的 C 入口**。"是 API 就得用 C"不成立，
"是引擎就得用 C++"也不成立 —— 真正的分界线是"这一层要不要给别人直接 include"。

## 欠缺清单（2026-11-14 实测，按优先级）

跟 Skia / 浏览器比，binUI 现在缺的东西都在这里，一条一条带证据（数字或代码行），并标了
**谁来填**（binUI 本体 / bin2d / bin3d / binGPU / 明确不做）。这是**欠账清单**，不是愿望单：
标"不做"的就是决定了不做，附理由，免得以后又从头讨论一遍。

### P0 — 决定"会不会输给 Skia"（可测的数量级差距）

| # | 缺什么 | 现在的证据 | 谁填 | 验收 |
|---|---|---|---|---|
| 1 | **层缓存 / 增量重绘**：内容没变的子树照样重算条带、照样重传顶点 | GL 每帧整块 `glBufferData`（`binui_gl-gdi.cpp:762`）；静态页也全量跑一遍 | binUI → bin2d（图层） | 静止页：0 次条带生成、0 字节上传 |
| 2 | **路径条带缓存有 1024 条硬上限**，超了就不缓存 | ✅ **已修（0.16.7）**：单节点上限 1024 → 16384，另加全局 65536 条预算（≈1.5 MB）。修之前 300×300 的 AA 图标实测 **1173 条带 / 199 µs**、几何不变也每帧重算（240×240 的 935 条刚好还能缓存，阈值是随机的） | binUI | 任意尺寸图标，几何不变时 0 重算 |
| 3 | **路径几何全在 CPU 且单线程** | 120×120 AA 图标 64 µs，300×300 199 µs（单线程 -O2 实测）→ 50 个图标 >3 ms | binUI（多线程）/ binGPU（三角形+stencil，会破契约） | 50 个图标 ≤2 ms |
| 4 | **每帧全量顶点上传**：没有"只更新脏节点"的通道 | 一个界面（12 渐变卡 + 8 纯色卡 + 16 图标 + 30 边框）≈1052 µs 生成 + **约 9800 个四边形/帧**（≈1.2 MB 顶点）；路径缓存命中也只是省了"算条带"，条带照样每帧重发 | binUI + binGPU | 静止页 0 字节上传；动画页只传脏节点 |
| 5 | **顶点预算有硬上限且超了是静默丢几何** | ✅ **已修（0.16.7）**：三端改成按需扩容（初始 10 万顶点，硬上限 100 万，撞上限只告警一次）。修之前三端都是 `kMaxVerts = 100000`（≈16,666 四边形 / 2 MB），`vertRoom()` 返回 nullptr 后 `emitQuad` **直接 return**；对照实验里把上限压到 1,200 四边形，64 个图标只画出 **20 个**，且不报错 | binUI | 200 个图标也不掉几何；打满时必须显式告警而不是静默 |

> 顺带一个已量到的数：半透明渐变卡 320×180 要 **240 条带**（逐行 AA 的代价），纯色卡只要 **1 条**。
> 20 张半透明卡 = 4800 个四边形，这是 P0-4 的主要来源。

### P2 — 明确不填（附理由）

- **GPU 路径光栅 / tessellation**：打破"后端只有 fillRect"这条契约，三端 0 diff 的像素基准随之
  报废；收益只在极端路径场景，不值。
- **文字次像素（ClearType）**：灰度 AA 在任意背景 / 缩放 / 旋转下都稳，次像素只在整数落位时
  成立，和 binUI "动画文字可亚像素"的方向直接冲突。
- **完整 SVG 滤镜栈 / SMIL / `<tspan>` 富文本**：投入产出比不成立 —— 这类素材应该在资产侧
  预处理成路径/位图。
- **通用图形 API 化**（bindless、光追、GLES·Metal 全家桶）：见 binGPU 那节的"明确不做"。

1. **离屏合成 → 组透明度 + 层缓存**：一套设施同时结掉 P1-7（正确性 bug）和 P0-1（数量级差距），
   这是唯一一个"差十倍"的地方，优先。
2. ~~顶点预算别静默丢几何（P0-5）~~ —— **已完成（0.16.7）**：三端按需扩容到 100 万顶点，
   撞硬上限才告警一次。
3. ~~去掉路径缓存的 1024 硬上限（P0-2）~~ —— **已完成（0.16.7）**：单节点 16384 + 全局 65536 条预算。
4. **路径几何多线程**（P0-3）：不动契约，纯并行。
5. 阴影 → 斜向渐变 → mip / 圆角图片（P1 那几条），按示例的真实需要排。

## bin2d —— 2D 绘制核

**定位**：保留模式的 2D 画布库（场景图 + 图层 + 合成），不认节点、不认布局、不认窗口，可以在
没有 UI 的地方用。宿主有两类：binUI 的 `<canvas>`，以及任何"要画点东西"的程序（报表、图表、
导出截图、票据打印）。

**语言**：C++17（和 binUI 同标准、同构建）；对外是 C++ 头，对下调 binGPU 的 C 头。

**要补的本体**（按实现顺序）：

1. **场景图**：`Scene → Layer → Shape`，形状 = 填充/描边/文字/图片/路径引用。现在 binUI 是
   "遍历节点树 → 现算条带 → 立刻 fillRect"，中间没有可保留的东西，所以每条路径每帧都重算。
2. **变换栈 + 裁剪栈的合并**：现在只有 `pushClip` 求交（轴对齐）；2D 库要有"任意变换 + 圆角
   裁剪 + 组透明度"，组透明度必须靠离屏合成，不能靠逐个形状乘 alpha（重叠处会露）。
3. **离屏目标与合成**：图层 = 一张 RGBA 位图，`blend(layer, dst)` 支持 `src-over`，再加
   `multiply` / `screen` 两三种就够。这一步顺带解决一个现成的痛点 ——
   `<canvas>` 里的内容**离屏渲染拿不到**（`tools/offscreen_render` 只能得到空画布，
   `docs/img/svgdemo|texturedemo|cubedemo` 三张图为此只能真机截屏）；有了离屏合成，
   canvas 内容也能进基准图和文档。
4. **滤镜**：投影、模糊（两次可分离盒式即可）、灰度/色相。投影是 UI 里最常要的，现在得靠
   半透明圆角叠一层来假造。
5. **图像重采样**：`drawImage` 现在任意尺寸都能画（后端是 bilinear 采样），缺的是**质量**：
   没有 mip 链（大图缩小会闪）、没有圆角裁剪、没有 tint、没有九宫格；2D 库要把这套补齐。
6. **导出**：`renderToRGBA()` 拿一帧位图 → PNG（自己写极小 PNG 编码，或直接 dump 裸 RGBA）。

**怎么抽**：新建独立目标 `bin2d`，源 = 现在的 `binui_path.h` + `binui_paint.h` + 新的
`Scene/Layer/Compositor`；binUI 变成它的**消费者**（`CanvasFn` 的参数从 `IBinUIGfx&` 换成
`bin2d::Canvas&`，应用写路径/图层，binUI 只负责把结果按条带刷到后端）。反向依赖不允许：
bin2d 里出现 `BinUINode`、`flex`、"节点盒"这些字眼就说明抽错了。

**开工条件**（满足任一）：

- 出现"多图层要合成 / 要投影 / 要组透明度"的界面，靠叠半透明圆角已经糊弄不过去；
- `<canvas>` 里的手绘代码超过一屏语义（现在 `svgdemo`/`texturedemo` 各百来行，还行）；
- 有非 UI 的宿主想直接用这套光栅（打印/导出是最可能的先来者）。

**验收线**：搬家那一版必须 **GL/VK/D3D11 三方像素基准 0 diff**、8 个示例无回归；功能扩展
放在搬家之后单独提，别混在一个提交里。

## bin3d —— 3D 渲染器

**定位**：小型实时 3D（场景图 + 相机 + 深度 + 光照），目标是"界面里嵌一块可交互 3D"，
不是引擎 —— 不追 PBR、不追后处理、不做资产管线。

**语言**：C++17；对下调 binGPU 的 C 头，横向直连 bin2d（C++ 对 C++）。

**现在的缺口**（都在后端，一条都不小）：

| 缺口 | 现状 |
|---|---|
| 深度附件 | 三端只有颜色附件，没有任何 depth/stencil |
| 用户着色器 | 各端一套固定管线；VK 的 SPIR-V 是 `src/backends/binui_vk_shaders.h` 里的常量数组 |
| 顶点/索引缓冲上传 | 顶点是每帧 CPU 生成的一整块常驻映射缓冲（见 `docs/vulkan_design.md` §5.1） |
| 相机/矩阵 | 完全没有；`examples/cubedemo` 里应用自己算 MVP、用 `fillLine` 画线框 |
| 贴图到面 | `fillRoundedXf` 的注释写明了：文字/图片**不参与**仿射（要像素对齐，旋转会糊） |

**路线（先说选哪条）**：**先软光栅，后 GPU**（GPU 阶段落在 binGPU 上，见下面「真不够用时」）。

软光栅版 = 三角形填充 + z-buffer + 双线性贴图，直接复用 bin2d 的扫描线与 `include/binui_path.h`
的求交，纹理走现有的 `prepareImageRaw`（RGBA 直传）通路。UI 侧只需要一个新的
`BINUI_3DVIEW` 节点类型：每帧把渲染结果当纹理上传，后端零改动 —— GDI 也能跑，离屏渲染也能出图，
像素基准可测。

好处是先把产品问题问清楚："嵌一块 3D 到底长什么样、要多快"。代价是 CPU：一个 640×360 视口
一帧就是 23 万像素的覆盖，软光栅能撑住 60fps 的覆盖量大概在 30 万像素以内（单个核），
再大就不行了。

真不够用时才进 GPU 阶段，而那条路走 **binGPU**（不是往 `IBinUIGfx` 里塞 3D 原语）：
`bingpu` 加网格创建 + 深度附件 + 自定义着色器，bin3d 只是它的调用者。**binUI 这边需要的仍然只有
"一张纹理"** —— 3D 视口渲染到 binGPU 的离屏目标，再把结果按 `prepareImageRaw` 的 RGBA 交给
`IBinUIGfx`，UI 的三个后端一行都不用改。这条分工是 binGPU 存在的另一个理由：它让"加 3D"不至于
变成"改三个 UI 后端"。

**这一步要提前认一件事**：3D 的像素基准不能再用"0 diff"——浮点光栅化顺序不同，z 缓冲边缘必然差
1 个像素，三端 diff 的容差规则必须重写（用覆盖率/轮廓容差，而不是逐像素比）。否则"三端像素
一致"这条底线会把 3D 拖成永远合不进去的分支。

**开工条件**（同时满足）：

1. 真出现"界面里要放能转的模型"的需求（不是"能画个立方体"，那个 `cubedemo` 已经能做）；
2. 软光栅版在目标视口尺寸上撑不住 60fps。

没到这两条就不做：3D 的工程量（驱动差异、着色器编译、资源生命周期）和 binUI 现在的验收方式
冲突，接进来会拖慢 UI 主线。

## binGPU —— GPU 抽象层（三个后端下面那一层）

**定位**：一份"设备 / 交换链 / 资源 / 管线 / 命令 / 呈现"的抽象，Vulkan 与 D3D12 各一个实现。
binUI、bin2d、bin3d 只写"怎么画"，不再各自维护一份交换链。

**语言**：**C11**，导出 C ABI —— 头文件里只有定长 POD + `uint64_t` 句柄 + 扁平函数，没有回调、
没有异常、没有 C++ 类型（理由与硬约束见上文「语言分工」）。

**为什么看起来该做**：同一件事现在写了三遍，而且每一遍都是完整的一份生命周期：

| 每份都要自己做的事 | 现状（`src/backends/`） |
|---|---|
| 设备 / 上下文 / 交换链 | `wglCreateContext` 9 处、`vkCreateSwapchainKHR` 5 处、`CreateSwapChainForHwnd` 2 处 |
| 管线 / 着色器程序 | `glCreateProgram` 4 处、`vkCreateGraphicsPipelines` 4 处、`D3DCompile` 3 处 |
| 着色器源码 | GLSL 内联 / `binui_vk_shaders.h` 的 SPIR-V 常量数组（101 行）/ HLSL 内联 —— **同一件事三套源码**，改一个 uniform 要动三个文件 |
| 代码量 | GL 1327 行、D3D11 1340 行、VK 2805 行（显式同步与描述符让 VK 自然是别人的两倍） |

`IBinUIGfx` 只约束了"怎么下发 7 个原语"，**没约束"设备怎么来"** —— 所以窗口、交换链、纹理上传、
present 阻塞语义这三件事在每个 `.cpp` 里各有一份，驱动差异的补丁也是三份。

**已经抽出来一半的东西**（binGPU 的地基）：

- `presentPacesFrames()`（`src/backends/binui_gfx.h`）：把"谁当节拍器"从三个外壳里提炼成一个
  接口返回值 —— 这正是 GPU 层该有的抽象形状；
- `docs/vulkan_design.md` §1 的六条契约、§5.10 的三路 present、§6.1 的鲁棒性清单，
  其实已经是 binGPU 的需求文档，只是现在还挂在 Vulkan 名下；
- VK 后端那套同步模型（fence + 单帧在上 + 帧内上传）是唯一一份"写对了"的显式同步代码，
  搬进 binGPU 就是它的 VK 实现。

**路线（先说选哪条）**：

1. **只抽一层薄的固定管线**：2D 四边形 + 纹理 + 深度附件 + 可选顶点上传，恰好覆盖
   `IBinUIGfx` 现在需要的，再加 bin3d 将来要的 `drawMesh`。
2. **先做 VK 实现**（照 `binui_vk.cpp` 已有的同步模型**用 C 重写**一遍，见下条），
   **D3D12 作第二实现**（替换 D3D11 那条路；D3D11 保留为老机器兜底，不迁）。
3. **GL 不迁**：状态机抽象收益最低，而它是老驱动 / 远程桌面 / 无 GPU 环境的兜底 ——
   迁过去只会得到一份"假装自己是现代 API"的 GL 封装。

**C 的额外成本要说在前面**：`binui_vk.cpp` 那 2805 行是 C++，搬进 binGPU 不是"移文件"而是
"按 C 重写"（没有 `std::vector` 存交换链 image、没有 RAII 管 fence、没有 `std::string` 拼错误）。
好消息是 Vulkan 自己的结构体本来就是 C 的，`VkDevice`/`VkCommandBuffer` 那套直接就能用；
坏消息是容器和生命周期要自己写，估计比重写一遍 D3D12 实现便宜不了太多。换回来的是一份**任何
语言都能直接绑**的 GPU 层 —— 这笔账在"第四份后端"出现时才划算，见下面的开工条件。

**明确不做的**：不追通用图形 API（bindless、pipeline cache 托管、光追、GLES/Metal 全家桶）。
一旦把它做成"跨平台渲染引擎抽象"，成本远超 binUI 本身，等于自己重写一个 wgpu。

**开工条件**（满足任一）：

1. bin3d 进到 GPU 阶段 —— 那时要网格 + 深度 + 自定义着色器，binGPU 的每个实现各写一遍；
2. 真要接第四个后端（Linux/X11、Android GLES、Metal），一次迁移要动的点超过"抄一份 `.cpp`"。

**现在不做的原因**：三个后端已经过了像素验收，而**像素一致的功劳恰恰在于"三份实现各自简单
直白"** —— 每份都只是把 `include/binui_paint.h` 算好的条带 `fillRect` 出去，出问题一眼能看出是
哪个后端、哪一行。中间插一层设备抽象，收益是"少写第四份"，代价是所有像素 bug 多一层要排查。
"第四份"还不存在时，这是纯亏。

**验收线**：搬家后三端像素基准仍 0 diff；窗口 / 输入法 / 拖边框外壳（`binui_app.h`、
`binui_gl-gdi.h`）**不认识 binGPU**，只认 `IBinUIGfx` —— 这条边界一旦被打破，这层抽象就白做了。

## 四层关系

```
bin3d  (C++17) ──►  bin2d 核 (C++17)（场景图 / 图层 / 合成 / 光栅数学）
                          ▲
binUI  (C++17) ───────────┘（并排的消费者：布局 + 事件 + 文本，用 2D 核画自己）
                          │
                          ▼
                binGPU (C11 / C ABI)（设备 / 交换链 / 管线 / 呈现）
                          │
                          ▼
                GL（兜底）/ VK / D3D12 —— 这三套 API 自己也是 C
```

四个独立目标（含现有的 binUI）、共用一份光栅数学，验收方式统一成"像素基准 + 三端 diff"。
语言边界只有**一条**：`binGPU` 的 C 头。上面三层都是 C++，谁都可以 `#include "bingpu.h"`；
下面的 GL/VK/D3D12 本来也是 C 接口，所以整条链上没有"语言转换层"这种东西。

**顺带的好处**：binGPU 是 C ABI，`bindings/` 里那三条语言（Python / Go / Rust）将来可以直接绑它
画 2D/3D，不必等 binUI 的 C ABI 一路扩到绘制原语。

**和 binUI 发布的关系**：这三个项目都不改 `.bui` 布局、不动 `BINUI_VERSION`，所以可以随时并行
推进；反过来，binUI 的版本号也不会因为它们的进度而冻结。

## 为什么现在只记不改

几何/光栅那层已经干净（纯头文件、无第三方依赖），抽出去的成本主要在**场景图/图层**这一块 ——
而它恰好是 binUI 现在**故意没有**的东西：binUI 每帧重算条带，换来了"没有缓存失效、没有脏状态"
（这在 0.16.x 那一串抖动/空转的 bug 里救过命）。

也就是说：把 2D 场景图加进来，等于给渲染器引入一份要维护的缓存生命周期。**这份复杂度只在
"画面要被复用 > 1 帧"时才有回报**（动画、图层、滤镜）。等真需求来了一次性做，别为了架构好看
先加状态。

三个项目的成本结构不同，别混着评估：bin2d 加的是**状态**（缓存生命周期），bin3d 加的是**另一套
光栅数学**（深度 + 浮点），binGPU 加的是**间接层**（少写第四份实现，但所有像素 bug 多一层）。
所以它们各自的开工条件也写在各自的章节里，不搞"一起开工"。
