# 11 - 阴影是「多层同心圆角矩形」画出来的：同一块面积被整块覆盖 2~5 遍

**状态**：待排期（0.32.0 的性能归因结论，未修）。
**类型**：performance（渲染路径） · **严重度**：中高（120Hz 目标的主要障碍之一）
**影响面**：所有画 `box-shadow` 的元素；四端都有（GL / Vulkan / D3D11 / GDI 走的是同一套环生成）。
**实测环境**：Windows 11 + MinGW-w64 gcc，`bin2d_window`（bin2d 后端）跑 `examples/buttonshow`，
1020×684，180 帧 headless，best-of-3；`BINUI2D_SKIP` 消融 + `BIN2D_TRACE_RR_DIRECT` 追踪。

> **2026-11 试做结论（先看这个）**：环带化**试过一轮，已整体回退**（bin2d 的 `FillRoundedRing` +
> binUI 的阴影环带化都没进版本）。两条硬结论：
> ① **性能是平账甚至倒退**：绘制 9.45 → **9.97 ms**（原因见 §9.1，环带路径没做成专用扫描线）；
> ② **像素必然变**：`ring + 内框实心` 与 `整块填充` **做不到逐字节相同**，最好情况也是 ±2
>   （AA 缝被算两次），实测 `pixels-bin2d` 的 shadow 用例 1.346% 不同、最大差 68（见 §9.2）。
> 所以这已经不是"性能优化"，而是**"要不要接受阴影像素变化"的决策问题**，需要 master 点头。
> 本轮不做；下一轮若重开，前提见 §9.3。

> 一句话：`box-shadow` 的高斯 falloff 被切成 N 个**整块**圆角矩形逐层叠画（累计 alpha 校正）。
> 每层都把内层已经盖过的面积再盖一遍 —— buttonshow 里 fillRounded 的 **63.8% 像素**是这种环，
> 而它换来的视觉效果只是一圈 2~7px 的柔和边缘。

---

## 1. 现象（数据）

`examples/buttonshow` 一帧：绘制 **9.45 ms** = fillRounded 6.56 + strokeRounded 1.69 + 其它 1.20
（`BINUI2D_SKIP=r/s/l/t` 消融测得，同机同负载）。present 2.9 ms，120Hz 预算 8.33 ms。

按逐次调用的追踪（`BIN2D_TRACE_RR_DIRECT=1`）统计这一帧的 131 次 `fillRounded`：

| 分组 | 组数 | 调用数 | 像素 | 占 fillRounded 像素 |
|---|---|---|---|---|
| 5 层同心组（按钮阴影） | 23 | 115 | 696 789 | 35.4% |
| 2 层同心组（卡片本体 + 1 个阴影环） | 8 | 16 | 1 273 484 | **64.6%** |
| 孤立填充 | 0 | 0 | 0 | 0% |

再按「本体（每组最小那层）vs 阴影环（其余）」拆：

| | px/帧 | 占比 |
|---|---|---|
| 本体 | 713 399 | 36.2% |
| **阴影环** | **1 256 874** | **63.8%** |

一个 5 层组（第一个按钮，全部同中心）：

```
x=33.4 y=92.4 131.1x53.1 r=15.6 a=3     ← 最外环
x=35.6 y=94.6 126.8x48.8 r=13.4 a=4
x=37.2 y=96.2 123.6x45.6 r=11.8 a=3
x=38.4 y=97.4 121.1x43.1 r=10.6 a=4
x=39.7 y=98.7 118.6x40.6 r= 9.3 a=2     ← 最内层（= 元素本体，border-radius:9）
```

2 层组是**大卡片**（`.card`）：本体 981×105 r=18.5 / 981×139 / 981×83 / 479×173 / 499×173 …，
各带 **1 个**阴影环（994.5×118.5 r=25.2，外扩 6.75px，a=3）。
它们只有 16 次调用却占 64.6% 的像素 —— **最大的单块不是按钮的 5 层，而是卡片的整块阴影环**。

## 3. 根因（代码位置）

1. `include/binui_paint.h:850 BuildShadowRings()`：把 CSS `box-shadow` 的高斯 falloff
   沿法线切成 N 个**同心圆角矩形**（`steps = ceil(A*255/3)`，上限 32；最外圈先画），
   每层做**累计 alpha 校正**：

   ```cpp
   rr.x = bx - k;        // 向外扩 k
   rr.w = bw + 2.0f * k;
   rr.radius = r0 + k;   // 半径同步
   rr.color = ((uint32_t)(a * 255.0f + 0.5f) << 24) | rgb;   // ← **同一 rgb**，只换 alpha
   ```

2. `src/backends/binui_draw_nodes.h:896`（轴对齐分支）/`:881`（仿射分支）：
   对每个环调用一次 `gfx.fillRounded(rr.x, rr.y, rr.w, rr.h, rr.radius, rr.color)`，
   也就是**每层都是一次实心圆角填充，覆盖整块面积**（不是环带）。
3. bin2d 后端 `src/backends/binui_bin2d.cpp:847 BinUI2D::fillRounded()` → `bin2d::Canvas::fillRounded`。

于是同一块区域被整块混合 N 次：512×512 级别的卡片一张 470 KB，远大于 L2，
5 层 = 同一批 cache line 写 5 遍。这也解释了「孤立微基准 0.32 ns/px、帧内实测 2.5 ns/px」的差距。

**颜色 / alpha 事实（band 方案的前提）**：
- 同一组的各层是**同一 RGB**，只有 alpha 不同（见上面 `| rgb` 那行）→ 累计 alpha 重算可行；
- 5 层组的 alpha 序列（内 → 外）= `2 → 4 → 3 → 4 → 3`，累计后总覆盖 ≈ **8%**（`1-∏(1-a/255)`），
  与 `.b` 的 `rgba(31,42,55,0.14)` / `.card` 的 `0.07` 量级一致。

## 4. 成本结构：**不要按面积线性折算**

「环带只覆盖 6.75px 厚」听起来是 8× 收益，实测不是 —— 因为环带的成本由
**每行两个短 span + 四个圆角弧的求交**决定，不是面积。用现有 `FillPath` 的双轮廓 + EvenOdd
（外层圆角矩形 + 内层圆角矩形，一次栅格化）实测：

| 形状 | 整块填充 | 环带（EvenOdd 双轮廓） | 环/整 |
|---|---|---|---|
| 按钮 131×53（6 961 px，厚 2.5px） | 27.8 µs | **23.8 µs**（448 ns/行） | **0.86×** |
| 小按钮 118×40（4 815 px，厚 2.5px） | 19.3 µs | **18.3 µs**（456 ns/行） | **0.95×** |
| 卡片 994×118（117 848 px，厚 6.75px） | 347.8 µs | **199.5 µs**（1 691 ns/行） | **0.57×** |

也就是说：**直接复用现有通用路径做环带，在按钮尺度几乎等于没省（0.86~0.95×）**，
只有大卡片能省到 0.57×；每行约 **450 ns**（小形状）/ **1.7 µs**（大半径卡片）是固定成本。

## 5. 两个候选方案与估算

### 方案 A（建议）：bin2d 加专用原语 `Canvas::fillRoundedRing(rect, radius, thickness, Paint)`

- 语义：外圆角矩形 **减** 内圆角矩形（EvenOdd 双轮廓），只覆盖环带。
- **不要**只调用 `FillPath`：那只会得到上表的 0.57~0.95×。要拿到量级收益，需要像
  `fillRounded` 的 0.14.0 快路径那样做**专用扫描线**（平移 + 纯色 + 无 mask 时：
  每行解析左右两个短 span + 圆角带，直接落像素，不落 Cover 缓冲）。
  参考：同尺寸 `fillRounded` 的专用路径是 **0.32~0.42 ns/px**，而通用 `FillPath` 是 2.95 ns/px。
- 估算（四层环带 + 1 次实心本体，按钮 131×53）：
  - 现状：5 次整块 × 6 961 px × **2.5 ns/px（帧内）** ≈ **87 µs/阴影**
  - 方案 A（专用环带快路径，按每行 ~0.7 µs 估）：4 × 53 行 × 0.7 µs + 1 次实心（≈17 µs）≈ **24 µs/阴影**
  - 全局：fillRounded 6.56 → **≈3.4 ms**（环带按 0.25× 计），绘制 9.45 → **≈6.3 ms**
  - 保守情形（每行 1.7 µs，即大卡片那种半径）→ fillRounded ≈5.4 ms、绘制 ≈8.3 ms
  - **结论：A 能改善 1.2~1.9×，但不保证单独就到 120fps（≤5.9 ms 绘制）**，最好和 strokeRounded 一起做。

### 方案 B（已否决）：换成真模糊（`popLayer` + `BlurSigma`）

131×53 按钮（6 943 px）实测：

| 方案 | 成本 |
|---|---|
| 真模糊：填充 16 µs + `Blur(r=6)` **85 µs** + 合成 25 µs | **126 µs/阴影** |
| 现有 5 层环（帧内 2.5 ns/px） | **87 µs/阴影** |

bin2d 的盒式模糊 ≈ **12 ns/px**（85 µs ÷ 6 943 px，与 `make quality` 里 512×512 r=8 的 14.6 ns/px 一致），
比「多画几遍 0.3~2.5 ns/px 的实心环」还贵 → **B 是倒退，不做**。

## 6. 三个必须一起处理的坑

1. **累计 alpha 要按带重算**：现在每层的 alpha 是「画在已被外层覆盖过的底色上」的增量校正；
   改成环带后每带的覆盖范围不同，必须重算成「该带的累计目标覆盖率」，否则内部会变淡/变深。
   （好在同组同 RGB，重算只需一条 `1-∏(1-a)`。）
2. **带缝 AA**：两个相邻环带的边界会各算一次覆盖率，接缝处可能出现 1px 的亮/暗线；
   需要「带边界共边」或按外轮廓单次 AA。
3. **像素会变 → 金标准要重出**：`make pixels` / `make pixels-bin2d` / `baseline-strict` 的
   金标准都需要重新生成，**需要 master 点头**（这是本次改动唯一不可逆的部分）。

## 7. 建议的实现顺序（供排期）

1. bin2d：加 `Canvas::fillRoundedRing(rect, radius, thickness, Paint)` + 专用快路径
   （平移/纯色/无 mask 时走扫描线；其余退回「双轮廓 EvenOdd FillPath」保证正确性）。
   **不给 `IBinUIGfx` 加新虚函数**（四端都得实现 + 金标准重出的代价太大，先不做）。
2. binUI：`BuildShadowRings` 的消费点改成「最外层以后各画一个环带 + 最内层画 1 次实心」。
3. 出图对比 + 重生金标准（master 点头后）。

## 8. 验收建议

- 微基准：131×53 的 5 层阴影从 **87 µs → ≤25 µs**；994×118 的卡片阴影从 ~290 µs → ≤100 µs。
- 端到端：buttonshow 绘制 **9.45 → ≤7.0 ms**（方案 A 的保守-乐观区间 6.3~8.3 ms，见 §5）。
- 像素：新旧差集中在阴影带缝与最外圈 AA（预期 ">1 级" 像素占比 < 0.5%），需要 master 明确接受；
  其余（文字、按钮本体、边框）必须逐字节不变。

## 9. 本轮试做记录（环带化，已整体回退）

试做内容：bin2d 加 `Canvas::fillRoundedRing(rect, radius, thickness, Paint)`（外圆角矩形减内圆角矩形，
外轮廓 + 内轮廓一起进同一套 8 子采样扫描线、EvenOdd 配对交叉点），
binUI 的阴影环消费点改成"外层各画 1 条带 + 最内层 1 次实心"。

### 9.1 性能：端到端**平账甚至倒退**（9.45 → 9.97 ms）

| 场景 | 绘制 ms | fillRounded+ring 合计（`BINUI2D_SKIP=r` 差值） |
|---|---|---|
| 改前（5 层整块填充） | 9.45 | 6.56 |
| 改后（外层 4 条带 + 最内层整块） | **9.97** | **7.31** |

拆开看：
- 卡片那条环 **347.8 → 199.5 µs**（省 148 µs × 8 条 ≈ **−1.2 ms**）✓ 有效；
- 按钮那条环 **2.2 → 23.8 µs/次**（× 4 环 × 23 组 × 92 次调用 ≈ **+2.0 ms**）✗ 把收益吃光。

原因是**这版 `FillRoundedRing` 不是专用扫描线**：它走 `Path → FlattenToDevice → BuildEdges → RasterEdges`，
每行都要扫整张边表 + 每次调用都重新做贝塞尔细分；而 `fillRounded` 的快路径是"不进 Path、中段行解析直写"。
两者差一个量级（0.32 vs 2.95 ns/px）。**这一条本轮没解决**（我加了中段解析行，但 r=0 分支有几何 bug，
见 9.2，且按钮尺度仍不达标）。

### 9.2 像素：**"环带 + 内框实心 = 整块填充"做不到逐字节相同**

独立验证（不经过 binUI，直接调 bin2d）：`fillRoundedRing(r, radius, t)` + `fillRounded(内框)`
对比 `fillRounded(r)`：

| 参数 | 不同像素 | 最大通道差 |
|---|---|---|
| a=40/255，r=12/18.5，t=2.5/6.75 | 440 / 287 | **±2** |
| a=3/255（页面里阴影的实际 alpha） | — | **±2~3** |
| r=0（矩形环）+ 分数偏移 | **679** | **255** ← 几何 bug，未解决 |

根因是数学上的：先画环、再把内框盖上去，是**两次 SrcOver**；而整块填充是**一次**。
在两者的 AA 缝上，`C_inner + C_ring(1-C_inner) ≠ C_outer`（例如各 50% 时是 0.75 vs 1.0），
差值被环的 alpha 限制在 `a·C(1-C) ≤ a/4`，所以 alpha 小的阴影只有 ±2~3；
但**它不是 0，也不可能是 0**（除非带边界做成硬边，那会出现锯齿）。
r=0 那批 255 的差异是另一个问题：矩形环的中段解析分支把左端像素漏掉了（左带起点晚 1px），
这是实现 bug，不是原理限制，但本轮没修完。

落地到 `pixels-bin2d`：`shadow` 用例 **1.346% 像素不同、最大通道差 68**，差异集中在阴影左右两条竖带。

### 9.3 结论与重开前提

**本轮不做。** 这条不是纯性能优化，而是"**要不要接受阴影像素变化**"的决策，需要 master 点头：
- 可接受范围大概是：阴影带缝 ±2~3（alpha 3/255 量级，肉眼不可见）、
  外圈 AA 的最大差 68（只在环带边界，1.3% 像素）→ 金标准必须重出；
- 其余（文字、按钮本体、边框、渐变）必须逐字节不变。

**若 master 接受，重开的前置条件（缺一不可）**：
1. **ring 必须做成解析 span 的专用路径**：每行算"外框 span − 内框 span"，
   中段行只写左右两条带、圆角行用与 `fillRounded` **同一套** 8 子采样（不是每行扫整张边表）。
   达标线：按钮 131×53 t=2.5 **≤6 µs/次**（现在 23.8），卡片 994×118 t=6.75 **≤60 µs**（现在 199.5）。
2. **修好 r=0（矩形环）分支**：中段解析行要覆盖"外框/内框都是矩形"的情形，
   并且外框左端像素不能漏（本轮实测差 679 px / 最大 255）。
3. 端到端必须低于改前的 9.45 ms 才算赢（本轮 9.97，平账偏负）。

**若 master 不接受像素变化**：这条路直接关掉，阴影优化只能走别的方向
（例如"同 alpha 的环合并成一次带 0.5px 硬边的填充"——同样会改像素，或干脆不动）。
