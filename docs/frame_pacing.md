## 0. 这轮盯的页面

![buttonshow：按钮样式一览（1020×684）](img/pacing-buttonshow.png)

它是"CSS 驱动 + 大量圆角 + 文字"的典型页面：一帧 234 次 `fillRounded`、20 次
`strokeRounded`、47 次文字，正好把三类成本都压在同一帧里。
# 帧节拍：为什么"平均帧率达标"仍然看着卡

> 这份文档记的是 binUI 0.32.0 那轮"动画太卡"的完整诊断链、修法与量测方法。
> 结论先行：**卡的直接指标不是 fps，也不是帧耗时，而是"帧间隔是不是刷新周期的整数倍"**。

## 1. 症状

master 的原话是"动画太卡了，感觉"。120Hz 屏、`examples/buttonshow` 1020×684 的稳态：

```
[perf] 240 frames  14.1 fps  total avg=25.81 绘制 avg=14.93 呈现 avg=10.88
[perf] 间隔直方图 2.75:93 3.00:128 3.25:2 4.00:1
```

帧间隔（相邻两帧"出帧时刻"之差）落在 **2.75 / 3.00 个刷新周期**两档上，各占一半。
平均帧率看不出来（14 fps 那是因为窗口被别的窗口盖住时 DWM 会把它掐到 ~1fps，
量测时必须把窗口置顶），但"一半帧吃 2.75 个刷新、一半吃 3.00 个"就是肉眼的一顿一顿：
2.75 不是整数，于是同一帧有时被合成 2 次、有时 3 次。

## 2. 量法：三个指标，缺一不可

| 指标 | 从哪来 | 回答什么问题 |
|---|---|---|
| 帧耗时（绘制/呈现分段） | `BINUI_PERF=1` | 慢在哪 |
| **刷新周期/帧**（`min/avg/max` + 直方图，0.25 周期一档） | 同上，0.32.0 新增 | 帧落点跟刷新边界对得上吗 |
| **抖动** = 间隔不是刷新周期整数倍的次数 | 同上 | 到底卡不卡（0 才是稳） |

以前只有"1ms 一档"的直方图：在 120Hz 上每档只值 1/8 个刷新周期，看不出拍子，
所以 0.31.1 及以前的所有量测都漏掉了这一项。

> **陷阱：不要用"平均 fps"验收动画。** 60 fps 落在 60Hz 屏上可以是 1.00 个周期（稳），
> 也可以是 0.99 个周期（每 8 秒掉一拍）。而 40 fps 落在 120Hz 屏上如果正好是 3.00 个
> 周期，看起来比 47 fps 的 2.55 个周期更顺。

## 3. 根因（三条独立的原因，都要修）

### 3.1 节拍分两条路，两条都不可靠

0.11.9 起，节拍按"present 会不会自己掐拍"分叉：

- **A 路**：后端 `presentPacesFrames()` 返回 true → 外壳认为相位归显示器，**完全放手**。
- **B 路**：否则外壳按 `nextFrameTime_ = now + 预算` 掐。

两条都有洞：

- A 依赖"交换链声明 vsync == 驱动真的阻塞"。在 DWM 合成下 `wglSwapBuffers(1)` 经常
  立刻返回（实测 0.3–2 ms）。外壳于是把自己的节拍器关掉了，帧落点完全自由漂移。
- B 的"现在 + 预算"**只保证至少隔一个预算**，落点相对刷新边界任意。

0.32.0 把它统一成一条规则：**下一拍必须落在刷新网格上**，闸门无条件生效；
`pacedByPresent()` 降级为只用于启动诊断（"慢在等合成还是慢在画"）。
给 bin2d 后端的 `presentPacesFrames()` 也改成了真问交换链（`bingpu_swapchain_info`），
不再写死。

### 3.2 present 每帧做一遍没用的反预乘

bin2d 的 `Surface` 本来就是预乘，`GpuCompositor::upload()` 却把它反预乘成直通
（698k px × 3 次整数除法 + 每帧一个 2.8 MB 临时 vector），而 binGPU 上传时再乘回去。
1020×684 的一次上传 **4.79 ms**。改成"预乘零拷贝直传"（`BGPU_TEXTURE_PREMULTIPLIED`，
binGPU 0.7.0 + bin2D 0.14.0）后是 **0.10 ms**。

### 3.3 非整像素对齐的圆角填充

UI 里大量元素落在 `.5 / .25` 像素上（居中、百分比布局、DPI 1.25/1.5）。
bin2D 0.13.0 的九段贴片路径只吃整像素对齐，非对齐的整条掉回 `Cover` 浮点缓冲
（2.7–4.3 ns/px）。buttonshow 一帧 234 次 `fillRounded` 里 131 次非对齐，占绘制 64%。
bin2D 0.14.0 的直接扫描线路径把它压下去（大卡片 1.99 → 0.32 ns/px）。

## 4. 修法：刷新网格 + 滞回

```cpp
// renderFrame 末尾（简化）
const auto endT = Clock::now();                 // 本拍**真正结束**的时刻（含 present 等的）
const double need = (endT - t) / grid;          // 本拍占了多少个刷新周期
long long k = frameSteps_;                      // 上一拍的档位（滞回用）
if (need > k)            k = ceil(need);        // 装不下：立刻升档
else if (k > 1 && need <= k - 1 - 0.15) --k;    // 降档：要留 15% 余量
frameSteps_ = k;
nextFrameTime_ = t + grid * k;                  // 钉在网格上
```

几个容易踩的点，都是实测踩出来的：

1. **基准必须是"本拍结束"而不是"本拍开始"**。从开始算的话，帧耗时一过整格，算出来的
   "下一拍"已经在过去，pump 立刻返回，间隔退化成"纯耗时"，又漂回非整数格。
2. **降档判据是 `need <= k-1`，不是 `k-1+余量`**。写成后者会让 `k=1` 却要在 1.2 个周期里
   画完，结果每帧都迟到，节拍反而更烂（实测退成 ~10 ms 的杂乱节拍）。
3. **网格起点要四舍五入**。`8.3333ms` 写成整数 µs 是 8333，`ceil(33333/8333)` 恰好进位成 5，
   于是 `BINUI_FPS=30` 在 120Hz 屏上变成 5 个周期（41.7 ms）而不是 4 个。
4. **相位只锚一次**。每帧 `DwmFlush()` 会把结束时刻硬贴到合成边界，代价是每帧多等最多一个
   周期 —— 实测 40 fps 与 60 fps 的差别就来自这一下，而它解决不了网格已经解决的东西。
5. **`invalidateAll()` 不能顺手砸掉相位**。它内部原本调 `requestFrameNow()`（`nextFrameTime_`
   置零），量测用的"每帧强制重画"（`BINUI_FRAME_EXIT`）走的正是它 —— 于是量出来的间隔
   根本没有参考价值。现在拆成 `markAllDirty()`（只标脏）+ `requestFrameNow()`（动相位）。

## 5. 怎么量才不会量错

这台机器（虚拟化）有两条坑，都会让你量出**假的 6 倍收益或 6 倍回归**：

- **单次读时钟约 40 µs**。`steady_clock::now()` 与 `__rdtsc()` 都是。所以按调用掐表的
  原语探针（`BINUI2D_PROF`）会把同一帧从 11.8 ms 量成 69.7 ms，而整进程 CPU 只多 2.7 ms。
  验证方法：跑同一份代码两次，看 `Get-Process` 的 `TotalProcessorTime` 有没有变。
- **窗口被盖住时 DWM 会把它掐到 ~1 fps**，量出来的"帧间隔"全是 800 ms 的停摆。

所以量测脚本固定做两件事（`build-mingw/tmp/measure.ps1`）：

```powershell
# 置顶 + High 优先级，然后才看数
[Win32]::SetWindowPos(h, HWND_TOPMOST, ...) ; $p.PriorityClass = 'High'
```

以及**用消融法归因**，不要用"每次调用掐表"：

```powershell
BINUI2D_SKIP=r   # 关 fillRounded    → 帧耗时差值 = fillRounded 的真实成本
BINUI2D_SKIP=s   # 关 strokeRounded
BINUI2D_SKIP=t   # 关文字
BINUI2D_SKIP=l   # 关图层（阴影/毛玻璃）
```

buttonshow 的消融结果（150 帧，绘制段）：

| 关掉的 | 绘制 ms | 差值 |
|---|---|---|
| 无（基准） | 9.45 | — |
| `fillRounded` | 2.89 | **6.56** |
| `fillRounded + strokeRounded` | 1.20 | 8.25（其中 stroke 1.69） |
| `drawText` | — | 0.57 |

## 6. 现状与下一步

0.32.0 之后：buttonshow 12.3 ms/帧（9.5 绘制 + 2.9 呈现），稳定吃 2 个刷新 → **60 fps，
抖动 2/239**。120Hz 的预算是 8.33 ms，所以还差 4 ms 才能锁 120 fps。

缺口与归属：

| 项 | 现状 | 归属 / 下一步 |
|---|---|---|
| `fillRounded` | 6.6 ms（帧内 2.5 ns/px，孤立基准 0.32） | 重叠：每个按钮 5 层同心圆角矩形共用 cache line。要减重绘或分块 |
| `strokeRounded` | 1.7 ms（20 次/帧，1px 环每段走四边形） | 同一条"边上解析覆盖率 + 破片直写"的思路还没用到它 |
| `present` | 2.9 ms | 已是 vsync 等待 + 0.6 ms CPU 工作，基本到地板 |

## 7. 补记：默认后端改成运行期选择之后（0.33.0）

![appshow 在 Vulkan 后端上（自动选择）：1280×800，112 fps](img/backend-vulkan-appshow.png)

0.32.0 那套帧节拍是**后端无关**的，所以 0.33.0 把默认后端换成 GPU（binGPU 探测，
VK > GL > D3D11 > CPU）之后，它一行没改也照样成立 —— 只多了一条：

- **present 自己等掉的那一拍不能再补**。VK 的 FIFO 交换链 present 会阻塞到刷新边界
  （实测 8.08ms），而网格逻辑还会在它之后补一整格 → 帧耗时 8.33ms 却按 2.03 个刷新
  周期出帧（120 fps 掉成 56）。判据用**实测的 present 耗时**（≥ 半个刷新周期 = 它自己
  等过了），不用后端声明。

> **0.34.0 起这一节的两个结论都要打折扣**：下表里 GL 的 105 fps 是"关不掉垂直同步"造成的
> 假象（见 §8.2），VK 的 112/55 两档是外壳和 present 互相等的双重等待。0.34.0 的权威数字
> 在 §8.5。

数字（同机、120Hz、200 帧）：

| 后端 | 帧耗时 | fps | 刷新周期/帧 | 抖动 |
|---|---|---|---|---|
| Vulkan（默认选中） | 8.50 ms | 112 | 1.07 | 1/179 |
| D3D11 | 0.75 ms | 113 | 1.07 | 0/199 |
| OpenGL | 1.48 ms | 105 | 1.14 | 1/199 |
| bin2d（CPU 光栅） | 12.11 ms | 56 | 2.13 | 2/199 |

注意 D3D11 那 0.75ms 是"没在等"的极端：它 present 不阻塞，所以完全靠外壳的网格
（1.07 个周期）—— 也就是说**节拍这件事在 GPU 后端上仍然由外壳负责**，这正是 0.32.0
那套网格存在的意义（不然 GPU 路径会按"能跑多快跑多快"漂在刷新边界之间）。
## 8. 补记：节拍器的归属（0.34.0）

master 2026-11-20 的追问把两件事分开了：

> 「按理说这种绘制请求 GPU 应该能画个几百上千帧才对。防止使用率过高，性能钳制才用的
> 节拍器（即达到屏幕或系统刷新率即可）。这个性能钳制在哪做呢？我感觉是在 bin2D/3D 这里，
> 当然做成可调的最好：标准/无限制/240/120/90/60/30 等」
>
> 「那个"标准"的意思是：跟着合成帧节拍或屏幕刷新率来决定：路性能不够时尽可能画多点帧，
> 性能超过时钳制在系统合成帧率」

### 8.1 先量：GPU 到底能画多少帧

窗口 1020×684，`bin2d::GpuCompositor::presentSurface` 死循环，**关掉仓里所有节拍器**
（`bin2D/build-mingw/tmp/present_probe`）：

| 后端 | vsync=0 | vsync=1 |
|---|---|---|
| Vulkan | 966–991 | 120.0 |
| D3D11 | 1846–1854 | 119.0 |
| OpenGL | 120.0（← 见 8.2） | 120.0 |

**结论：帧率从来不是画出来的上限。** 一帧 0.5–1.0 ms，也就是说上千帧的算力一直摆在那里，
被节拍器掐成了 55/31/100 这些数字。

### 8.2 顺手挖出来的两个真 bug

| bug | 现象 | 根因 | 修法 |
|---|---|---|---|
| `wglSwapIntervalEXT` **从来没被装载过** | 传 `vsync=0` 也仍然每帧等刷新：120.0 fps / 8.335 ms | `bingpu_gl.cpp` 里只声明、没进装载表（`loadGlFunctions` 的 `BGPU_GL_FN` 名单里没有它），于是 `if (g_gl.wglSwapIntervalEXT)` 恒假；驱动默认 interval=1。binUI 的 `binui_gl.cpp` 犯的是同一类错：只在 vsync 为真时调 `(1)`，为假时**不调** —— 而"不调"等于保持 1 | 两处都改成**两个方向都调** |
| 可等待定时器**晚 ~1.0 ms** | 240 fps 档只跑到 163，60 档跑到 57.8 | `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` 在本机是对齐到 ~1 ms tick：请求 1/2/4/8/16 ms 的中位迟到是 967/999/1000/949/821 µs；而请求 500 µs 只迟到 16 µs | 请求时间提前 900 µs（`build-mingw/tmp/timer_probe` 是那次量测的探针） |

修完 GL 的 `vsync=0`：**120.0 → 801 fps**（同一个 context、同一个窗口）。这条很重要 ——
以前"GL 100 fps 最稳、VK 55、D3D11 31"那张表里，GL 的数字根本不是它的能力，是它**关不掉**
垂直同步。

### 8.3 节拍器该放在哪：策略在 bin2D/bin3D，闸门在 binGPU

三条依据，缺一条都不成立：

1. **判据全在设备层**：刷新率、present mode、present 到底有没有阻塞到垂直同步、
   上一拍 present 花了多久 —— 上层只能猜。0.33.x 在外壳里猜（"present 耗时 ≥ 半个刷新
   周期就当它等过了"），Vulkan 上猜错就是**双重等待**：present 等一格 + 外壳再补一格
   → 120 Hz 屏上 55 fps，而同一份代码裸跑 present 是 119.9 fps。
2. **意图在绘制语义层**："这个画布最多一秒出多少帧"是绘制策略，属于 bin2D/bin3D。
3. **执行在外壳**：只有外壳能"睡到某个时刻同时保持消息可唤醒"。

所以切口是：**`bin2d::GpuCompositor::setPacePolicy()` 给策略，`bingpu_pace_*` 算闸门，
外壳只问一句 `paceWaitUs()` 然后睡。** binUI 里原来那 60 行网格 + 滞回 + 启发式
全部删掉（只剩"没有设备层的遗留后端"用老网格兜底）。

规则一句话：**下一拍 = max(本拍开始 + 目标周期, 本拍结束)**，且

- present 自己在等刷新时，相位改从**本拍结束**起算（`end + (k-1) 格`）：
  它返回的时刻本来就是刷新边界，从这里数才不会和刷新打拍子；
- `标准` **不向上凑整**：画不完就尽力多画（9.5 ms 的帧就是 ~105 fps），
  不为了"整数个刷新周期"退成 60 fps；
- 只有明确要 60/30 时才凑整（那是策略自己给的约束）。

### 8.4 可调档位

```powershell
$env:BIN2D_PACE = 'standard'   # 默认：上限=刷新率，下限不设
$env:BIN2D_PACE = 'unlimited'  # 不掐拍（自动关 vsync；会撕裂）
$env:BIN2D_PACE = '240' | '120' | '90' | '60' | '30'
```
`BINUI_PACE` 是别名；`BINUI_FPS` 保留为兼容写法（`0` = unlimited）。解析表只有
binGPU 那一份（`bingpu_pace_policy_parse`），上层只负责把字符串转下去。

**90 fps 落在 120 Hz 屏上实际是 120 fps** —— 只能取整数个刷新网格，而
`bingpu_pace_frame_ms()` 报的是**生效**周期（8.33）不是名义周期（11.11）。
不许出现"声称 90、实际 120"或者"声称 90、实际 60"。

### 8.5 实测（buttonshow 1020×684，120 Hz 屏，240 帧 × 3 次，报 min–max）

| 后端 | 节拍 | fps | present | 说明 |
|---|---|---|---|---|
| Vulkan | **unlimited** | **2116–2207** | 0.21 ms | 画 0.31 ms/帧，就是这个数 |
| D3D11 | unlimited | 1893–2491 | 0.15 ms | |
| OpenGL | unlimited | 702–729 | 0.86 ms | 还要付每帧 `glReadPixels` |
| Vulkan | standard | 114.3–114.6 | 8.38 ms | 绝大多数帧精确 1.00 个刷新周期 |
| D3D11 | standard | 115.7–116.2 | 8.23 ms | |
| OpenGL | standard | 108.2–108.6 | 7.82 ms | |
| Vulkan | 120 | 111.9–112.9 | 8.27 ms | |
| Vulkan | 240 | 201.6–212.7 | 0.27 ms | 比刷新快 → 自动关 vsync；VM 上到 85% |
| Vulkan | 60 | 58.6–58.7 | 8.48 ms | |
| Vulkan | 30 | 29.9–30.0 | 8.48 ms | |
| bin2d（CPU 光栅） | standard | 92.9–95.9 | 1.39 ms | 绘制 9.0 ms 装不下一个刷新 → **尽力多画**（0.33 是 56） |
| bin2d | 60 | 61.6–61.8 | 1.96 ms | |

两条要留意：

- `unlimited` 的「抖动」百分比没有意义（间隔本来就小于一个刷新周期），看 fps 就行；
- `standard` 在 CPU 光栅上「抖动」接近 100% 也**不是节拍错了**：一帧 10.3 ms 画不完
  8.33 ms，间隔本来就不可能是整数倍。按 master 的口径这就是"路性能不够 → 尽可能多画"，
  所以 perf 行里会附一句"一帧画不完一个刷新周期"。
