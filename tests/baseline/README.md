# tests/baseline —— 迁移基线快照

**这份目录里的 `manifest.txt` 提交进仓库，别手改。** 它记录的是"开始把 binUI 的路径光栅
迁到 bin2d 之前"那一刻，三端像素、原语流、画质数字的指纹。

生成/校验工具：`tools/baseline_snapshot.cpp`（口径见 `tools/README.md`）。

```sh
mingw32-make SHELL=sh baseline          # 重生成快照（三端各渲一遍 + draw_bench + 画质）
mingw32-make SHELL=sh baseline-check    # 对快照：报告哪一端、哪个用例动了
mingw32-make SHELL=sh baseline-strict   # 同上，但哈希/画质有任何变化就失败
```

## 为什么要有它（像素回归不够用）

`make pixels` / `pixels-vk` / `pixels-d3d11` 只回答"在容差内吗"。迁移期间真正要回答的是
**"动的正好是该动的那些，别的一个都没动"** —— 容差是 0.5% 像素、通道差 8，一个真实的
退化完全可能躲在这条线内（比如整页文字从抗锯齿变成硬边只影响 0.3% 的像素）。

所以这里换了个问题问代码：**给我指纹，我自己看差在哪。**

## 判据分两级（别混）

| 层 | 谁负责 | 回答什么 | 失败了怎么办 |
|---|---|---|---|
| 硬门禁 | `pixel_diff`（`make pixels` 等） | 能不能接受（容差内 / 跨后端一致） | 修代码 |
| 快照 | 本目录 + `baseline-check` | 到底动了什么 | 看清清单，再决定是修还是更新快照 |

`baseline-check` 的退出码：

- **用例增删、尺寸变化 → 失败**（这是结构变化，不是渲染细节）；
- **哈希 / 画质变化 → 默认只报告**（迁移阶段本来就该变几个像素，该不该变由人看清单）；
- 加 `--strict` 时哈希也当作失败 —— 用于"这一步必须逐位相同"的步骤（比如纯重构）。

## manifest.txt 长什么样

```
px   <后端> <用例> <W>x<H> <FNV-1a 64>     # 后端 = gdi / gl / vk / d3d11
draw <用例> <原语流哈希>                    # draw_bench --frames 1 --warm 0 --hash
qa   <序号> <bin2d make quality 的原文>      # 画质参照
```

哈希算在**原始 ARGB**（宽高 + 逐行像素）上，不是 PNG 文件字节 —— 换个 PNG 编码器也不会
让快照失效。

用例集合 = `pixel_diff` 的那 18 个用例（四端都有）+ 4 个整页示例 + 28 个动画中途帧用例
（只有 GL/VK/D3D11，GDI 侧本来就没有基准图）：

| 组 | 条数 |
|---|---|
| `px gdi` | 18 |
| `px gl` / `px vk` / `px d3d11` | 各 50 |
| `draw`（原语流哈希） | 9 |
| `qa`（bin2d 画质数字） | 11 |
| 合计 | **188** |

`animshow` 不在 `draw` 里：它的原语流由动画时钟（wall clock）决定，同一份代码连跑三次
给三个不同哈希 —— 拿它当基线只会每次报"变了"。像素快照没这个问题（渲染工具定帧，
两次全渲 168 项逐位相同）。

## 什么情况下允许 `make baseline` 重生成

1. **能逐条解释变化**：对着 `baseline-check` 的清单说得出"这个用例为什么变、变在哪一端"；
2. 在 `CHANGELOG.md` 写清这一条（"哪些用例的指纹变了、为什么"）；
3. 硬门禁先绿（`make pixels` / `pixels-vk` / `pixels-d3d11` 全过）。

三条缺一条就不要更新快照 —— 更新快照很容易，难的是事后还知道它为什么变。

## 它不是"理想值"

已知差异照样记在快照里，不做修正：

- GL 与 Vulkan 的 4× MSAA 在斜边上采样归属不同（同一个 GPU、两套驱动前端），
  所以同一用例的 `gl` / `vk` 指纹本来就可以不同；
- D3D11 还留着自己的圆角模板与文本光栅化（P7b 才换），`d3d11` 与 `gl` 的差异也是已知的。

快照记的是**此刻的事实**，不是"应该的样子"。要判"该不该有差异"看
`docs/future.md` 的已知差异清单和 `pixel_diff` 的容差判据。
